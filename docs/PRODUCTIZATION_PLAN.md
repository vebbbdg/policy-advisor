# 留学生政策助手（CPT/OPT 垂直领域）产品化规划

## 背景与核心判断

现有资产可直接复用：FastAPI + SSE 流式 + 多会话 + 上传安全 + 三臂检索（dense/hybrid/rerank）+ 评估框架 + Docker。
垂直化要解决的三个新问题：
1. **跨语言检索**：语料是英文官方文件，用户用中文提问 → all-MiniLM-L6-v2 跨语言能力弱，必须换多语言嵌入模型
2. **政策时效性**：政策频繁变动，每条答案必须带"来源 + 生效日期"，检索结果需携带抓取时间元数据
3. **合规红线**：移民政策回答必须声明"不构成法律建议"，超出语料范围必须拒答

---

## 阶段 0：项目初始化（开工第 1 天）

**决策：新起项目目录 + GitHub 新建仓库，原项目完全不动。**
- 简历叙事：两个定位清晰的项目（通用 RAG 平台 / 政策垂直产品）优于一个混合项目；原项目已是完整自洽的简历 bullet，不稀释
- 风险隔离：换嵌入模型、重建向量库、加认证等破坏性改动不影响原项目的"开箱即跑、测试全绿"完成态
- GitHub 操作：新建仓库（不用 Fork）；首个 commit 放 chat_robot 基线代码，注明 `chore: baseline from chat_robot (MIT)`；README 链接回原仓库，讲述"将自己的 RAG 平台产品化"的迭代故事；原仓库保持冻结不再修改
- 新目录命名建议：`policy-advisor` 或 `visa-policy-bot`（建仓库时定）
- 后续所有阶段的路径均指新项目目录；`crawler/`、认证、持久化等新增模块全部落在新仓库，形成独立的 0→1 commit 历史（符合小步提交、说明"改了什么为什么"的习惯）
- 唯一例外：在垂直化过程中沉淀的**通用性修复**（如与业务无关的 bug 修复），可选择性地以小 commit 同步回原仓库，但非必需，MVP 阶段默认不回写，避免分心

## 阶段 1：政策语料建设（第 1 周，产品核心）

### 1.1 语料源清单（官方来源）
- USCIS：OPT/CPT 页面、Policy Manual Vol.2 Part F（学生章节）、I-765 表格说明
- ICE / SEVP：Study in the States 网站的 OPT/CPT 指引
- DHS 联邦公报：政策变更公告
- 2-3 所代表高校的 ISSO（国际生办公室）页面：补充实操流程（如 CPT 申请步骤）

### 1.2 新增 `corpus/` 语料管道
- 新建 `crawler/` 目录：爬取脚本（requests + BeautifulSoup），输出结构化 Markdown
- 每份文档记录元数据：`source_url`、`crawl_date`、`policy_topic`（CPT/OPT/STEM_OPT/H1B）、`content_hash`
- 存储到 `data/policy_corpus/`，与生产向量库分离，支持版本化（git 管理语料快照）
- 入库走现有 `rag_engine.add_document`，但需扩展 chunk metadata 携带来源与日期

### 1.3 政策变动监控（轻量版）
- 定时任务（GitHub Actions cron，每周一次）重爬语料源，对比 `content_hash`
- 有变动时输出 diff 报告（Issue 通知），人工审核后重新索引——MVP 阶段不做全自动更新

## 阶段 2：RAG 链路垂直化改造（第 2 周）

### 2.1 嵌入模型切换（关键技术决策）
- `core/model.py`：嵌入模型从 `all-MiniLM-L6-v2` 换为 `paraphrase-multilingual-MiniLM-L12-v2`（同生态、零成本、中英跨语言）
- 用现有 `eval/` 框架做 A/B 验证：旧模型 + 翻译层 vs 多语言模型，用数据定夺
- 注意：切换模型后必须清空 `data/vectordb` 重建索引（项目已知约束）

### 2.2 引用与时效输出
- `main.py` 的 `format_context` 流程扩展：检索结果返回 `source + crawl_date`，SSE payload 增加 `citations` 字段
- 前端 `static/index.html`：答案下方渲染"来源与政策日期"卡片
- 系统提示词重写：移民政策顾问人设 + 强制引用来源 + 答案附"信息截至 {date}，以 USCIS 官网为准"

### 2.3 拒答与合规
- 复用现有 3 条"无法回答探针"评估机制，扩展政策域版本：问非移民话题（如写代码）必须拒答并引导回政策话题
- 每条回复固定追加免责声明："本内容为信息参考，不构成法律建议，重大决策请咨询学校 DSO 或移民律师"

### 2.4 政策域评估集
- 替换/扩展 `eval/dataset.json`：25+ 条政策 QA（CPT 资格、OPT 90 天失业期、STEM OPT 延期、H-1B 抽签等），含英文原文 ground-truth 与中文问法
- 验收标准：Recall@3 ≥ 0.9，MRR ≥ 0.95，拒答探针 100% 通过

## 阶段 3：产品化工程（第 3 周）

### 3.1 数据持久化（MVP 必需）
- 当前 `core/session.py` 是内存态会话，重启即丢 → 迁移到 SQLite（SQLModel），存会话与消息
- 会话数据按用户隔离（见 3.2）

### 3.2 轻量认证
- MVP 方案：邮箱 + 验证码登录（或 Google OAuth 二选一，实现时定），JWT 签发
- 新增 `core/auth.py` + `/api/auth/*` 端点，会话/聊天接口挂认证依赖
- 未登录可用访客模式（限 5 条消息），引导注册——获客转化设计

### 3.3 防护与稳定性
- 速率限制：slowapi，每用户 20 次/小时（防 API 费烧穿）
- LLM 成本上限：日预算告警（日志统计 token 消耗）
- `core/rag.py` 已知生产链路走 dense 检索，评估通过后可切换 `RETRIEVER_MODE=rerank`（延迟 +0.5-1s，需基准测试确认）

## 阶段 4：部署上线（第 4 周）

### 4.1 托管方案（决策：Render，学生友好且支持持久卷）
- FastAPI Docker 镜像部署到 Render（现有 Dockerfile 直接复用，需移除 reload 模式）
- Chroma + SQLite 数据挂载 Render Persistent Disk
- 备选：Fly.io（同样支持卷）；暂不上 AWS，MVP 阶段控制运维成本

### 4.2 域名与前端
- 购买域名（如 policyhelper.ai 类，注册时再定），Render 自动 HTTPS
- `CORS_ORIGINS` 收紧为实际域名（现有环境变量机制直接可用）

### 4.3 CI/CD
- GitHub Actions：PR 跑 `pytest tests/` + `python -m eval.run_eval`（检索指标，无 API 成本）
- main 分支合并自动部署到 Render

### 4.4 监控
- 复用 `/api/health`，配 UptimeRobot 免费监控
- 查询日志落盘（已有结构化日志），每周人工分析高频问题反哺语料

## 阶段 5：上线后合规与运营（第 5 周起，持续）

- 全站页脚免责声明 + 隐私政策页（用户邮箱仅用于登录，不出售数据）
- 语料库标注"最后更新日期"，政策变动时优先更新受影响主题
- 收集真实问题 → 补充评估集 → 迭代检索配置（闭环复用现有三臂实验方法论）

## 测试与验收

| 验收项 | 标准 |
|---|---|
| 政策域检索质量 | Recall@3 ≥ 0.9，MRR ≥ 0.95 |
| 拒答探针 | 域外问题 100% 拒答 |
| 单元测试 | 现有 55 个测试全绿 + 新增认证/持久化测试 |
| 端到端冒烟 | 线上：注册 → 提问 → 流式回复带引用 → 重启后会话不丢 |

## 风险与假设

- 爬取官方站点需遵守 robots.txt 与速率限制，仅低频抓取公开页面
- 多语言嵌入模型在政策术语（CPT/OPT/STEM）上的检索效果需阶段 2 实测，不达标则回退"查询翻译 + 英文关键词混合检索"方案
- MVP 暂不做付费墙、移动端原生优化、多模型切换
